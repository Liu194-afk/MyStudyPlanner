Ethics & Privacy

Even a tiny study app stores personal stuff - which courses I take, what's due, and how I describe my own work. This page explains what I actually did in the code to handle that data properly, rather than just saying "privacy matters".

Things that support ethical data use

I only collect what's actually needed

The task form asks for six things: title, course code, course name, due date, description and notes. It doesn't ask for a real name, email, student ID or location. Data I never collect can't be misused or leaked, which is the easiest win.

Validation that's honest, not silent

Everything is checked before it gets saved. Required fields can't be empty, the course code has to look like a real one (e.g. INFO1012), and a due date that's not a real date or is already in the past gets rejected with a message like "Due date cannot be in the past." The app never pretends it saved something it actually refused.

Deleting always asks first

A deleted task is gone for good, so the app always confirms first. The dialog names the exact task, like "Delete 'Assignment 3' (INFO1012)?", and the safe button (Keep task) is the one focused by default, so it's hard to delete something by tapping too fast.

Things that support data privacy

Data never leaves the browser

Tasks are saved in the browser's localStorage under a key for the logged-in user (msp-tasks-student). The site makes no network requests at all - no server, no database, no third-party scripts - so the task list physically stays on the user's own device.

Login with a short-lived session

You can't see the task workspace without logging in. The login state lives in sessionStorage, which the browser wipes when the tab closes. On a shared computer (like the ones in the uni labs), closing the tab is enough to keep the next person out.

No tracking at all

The site only loads its own files: one stylesheet, three JavaScript files and some images I drew myself. No cookies, no analytics, no ad scripts, no external fonts - so no third party can watch when or how the site gets used.

Limitations, honestly

Two things are worth admitting. First, localStorage isn't encrypted, so someone with physical access to the same computer and browser profile could read it - one more reason not to collect sensitive details in the first place. Second, the login is a hard-coded demo account (student / info1012) because this is a course assignment; a real product would check passwords on a server and store them as hashes instead of plain text in a JavaScript file.
